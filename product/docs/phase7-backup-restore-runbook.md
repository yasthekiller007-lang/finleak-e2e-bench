# Phase 7 backup and restore qualification

Internal targets are RPO ≤1 hour and RTO ≤8 staffed hours; they are not an SLA or measured provider result. Real provider backup schedule, encryption, isolation, source versions, WAL/PITR coverage, alert delivery, permissions, staffed operators and a timed managed restore remain **external evidence pending**. No infrastructure was provisioned or deployed.

## Supported restoration contract

Use a PostgreSQL 17 **native physical cluster backup/PITR** that genuinely preserves original transaction identity and commit-timestamp history, plus exact private original-object versions. [pg_basebackup](https://www.postgresql.org/docs/17/app-pgbasebackup.html) with streamed WAL and a SHA-256 manifest, followed by [pg_verifybackup](https://www.postgresql.org/docs/17/app-pgverifybackup.html), is the engineering drill. Manifest verification alone does not prove application/financial/source recovery.

A logical SQL restore creates a new cluster and new xmin/commit timestamps. It is **not a supported route to restored Phase 6 authority** under `pilot-native-restore/1`, even when it copies captured publication rows. Do not start serving it as an authoritative application or run publication capture to repair its missing historical K. Comparison rejects a changed PostgreSQL system identifier and any changed uncaptured original commit witness. No created_at substitution, timestamp inference, backdated publication or monetary recalculation is permitted. A later independently qualified authentic-provenance reconciliation design would require separate review; this task does not invent one.

For native restoration, already captured RecoveryPublication remains byte/value identical. For an uncaptured financial commit, PostgreSQL must still return the authentic original `pg_xact_commit_timestamp(xmin)` from preserved cluster history. Missing/expired provenance blocks qualification. The validator never writes publication metadata or any authority. Subsequent metadata retry, where original provenance remains available, uses the existing explicit authorized Recovery Ledger workflow; an operator restore tool does not perform it automatically.

## Procedure — protected isolated environment only

1. Obtain explicit incident/restore and environment authorization. Suspend traffic and quiesce writes under the access/incident runbooks. Preserve the donor, existing backups/WAL and exact private object versions. Never erase originals/history to recover space or make a downgrade pass.
2. Use a separately protected backup identity, encrypted storage/transport, least privileges and private destinations. Keep runtime credentials, restore manifests, DB dumps and source bytes out of CI/public artifacts/logs/command-line URLs. Provider identity/region/subprocessor/retention remains a separate approved operating choice.
3. Capture a protected consistent read-only baseline with `app.operations.restore_validation.snapshot` using a REPEATABLE READ connection and actual private byte storage. It hashes complete financial/review/proof/recovery/operational/audit rows without printing their content, recomputes canonical proof fingerprints, hashes guards/functions/roles/table and column grants, and records genuine uncaptured commit witnesses. Administrative catalog access is operator-only, never granted to the ordinary app.
4. Preserve a full native backup plus required WAL and coordinated original-object version inventory. Record backup start/end/LSNs, source snapshot/versions, exact release/schema/profiles, operator/date and the last successful backup/loss window. A backup of DB alone does not satisfy the requirement. Keep source preservation/deletion permissions separate.
5. Restore into a **new isolated native cluster**, with no customer traffic and no privileged app account. Verify the backup manifest, PG17/commit tracking/current schema, all trigger/function/role grants and original sources. Do not activate normal financial APIs before qualification.
6. Run `python -m app.operations.restore_validation --expected <protected-original-snapshot.json>` against the isolated target. Configured storage must point to its protected restored originals. All exact digests, native cluster identity, original K witnesses and actual SHA/size inventory must match; unavailable/corrupt sources, changed guard/grant/function, missing provenance or any bound yields explicit failure. Bounds: 20,000 total rows, 50 MiB internal canonical data, 1,000 originals, 100 MiB actual source reads and 25 seconds; no partial comparison becomes PASS.
7. Record actual restored reporting/proof/recovery and role/admission checks, lost interval, restore/reconciliation elapsed times and primary/deputy sign-off. Validate actual cloud object version privacy and genuine provider PITR before claiming RPO/RTO. The tool's PASS is comparison evidence, **not release/deployment/pilot authorization**.
8. Resolve differences by authentic restored evidence and an explicitly approved incident route; do not fabricate missing K, rewrite financial history, recalculate old money or silently generate/repair/review/succeed proofs. Retain the failed rehearsal and unresolved blockers. Obtain separate release/deployment authorization only after every pilot gate passes.

## Engineering drill and limits

`acceptance.restore_integration` is CI-only, synthetic and excluded from production images. It creates its own three isolated disposable PostgreSQL 17.11 clusters. Existing explicit domain API fixtures create a reviewed finding, complete proof, approved partial recovery and real post-financial-commit/pre-publication interruption. It preserves captured and uncaptured history, takes/verifies a native backup, boots a separate target, copies exact synthetic originals and compares all protected digests/roles/guards/fingerprints/original K. It injects source tampering and performs a real logical SQL copy into a third cluster to verify rejection of its new provenance. It never touches a production database or source.

The fixture identity/scanner are test-only engineering mechanisms, not real IdP or engine qualification. Actual private ClamAV and S3 jobs remain separate evidence. CI restore is not managed PITR, real backup scheduling, object cloud persistence, an RPO/RTO guarantee or a production restore. P0-22/23 stay external evidence pending until the actual approved topology and staffed drill pass. Backup/deletion duration, legal holds and offboarding erasure require separately approved policy; no universal retention or compliance claim is made.
